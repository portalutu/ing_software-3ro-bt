Antes de comenzar

Una aplicación web tiene un frontend, que muestra la interfaz y responde a las acciones del usuario; un backend, que recibe solicitudes y aplica reglas; y, a menudo, una base de datos, que conserva información. El navegador y la API intercambian mensajes mediante HTTP. En este ejemplo, el usuario envía un formulario de acceso, el servidor busca su cuenta y devuelve una respuesta que el navegador debe interpretar.

Para localizar un error, recorre las etapas en orden y busca la primera evidencia que falta o es incorrecta. Un mismo síntoma, como “no puedo iniciar sesión”, puede tener causas en lugares diferentes. Este esquema representa el flujo de información de una aplicación; no es un DFD formal con notación de procesos, entidades y almacenes.

Petición

Mensaje del navegador al servidor: URL, método, cabeceras y, si corresponde, cuerpo.

Respuesta

Mensaje de vuelta: código de estado, cabeceras y datos o descripción del error.

Evidencia

Lo observable en Console, Network, registros del servidor y base de datos.

B · ¿Cómo diagnosticar un corte?

Observa una etapa por vez

Compara lo que debería pasar con lo que realmente ves. La primera diferencia acota el problema.

Ejemplo: el clic ocurre ✓ → Network muestra 404 → el servidor tiene otra ruta → corrige la URL del frontend y vuelve a probar.

Atajo de laboratorio: abre las herramientas de desarrollo (F12), observa Console y Network, reproduce el error y compara sus datos con los registros del servidor. Un 404 indica que esa URL no encontró un recurso; un 405 puede señalar un método no permitido; un 500 indica un error del servidor. El código por sí solo no demuestra la causa exacta.
